# Requirements Document

## Introduction

This feature introduces a Direct Token (API Key) authentication mechanism for the go-tunnel CLI client. Currently, the CLI agent must go through an interactive login flow (username + password → JWT token) before establishing tunnels. This feature allows users to generate long-lived API keys from the Web UI that can be used directly by the CLI client to establish tunnels without interactive login. This is essential for headless/automated deployments, CI/CD pipelines, and server environments where interactive login is impractical.

## Glossary

- **API_Key**: A cryptographically-secure, random token string generated by the system that grants tunnel access on behalf of a specific user. Stored in PostgreSQL with metadata (name, expiration, owner).
- **Token_Generator**: The Web UI component (page + API endpoint) that allows authenticated users to create, view, and revoke API keys.
- **Token_Store**: The PostgreSQL table (`api_keys`) that persists API key records including the hashed key value, owner, name, expiration, and status.
- **Tunnel_Server**: The Yamux-based TCP server that accepts agent connections and validates authentication tokens during the REGISTER handshake.
- **CLI_Agent**: The `gotunnel-client` binary that connects to the Tunnel Server and forwards traffic through the tunnel.
- **Auth_Usecase**: The business logic layer responsible for verifying tokens (both JWT and API keys) and resolving them to a User entity.

## Requirements

### Requirement 1: API Key Generation

**User Story:** As a user (admin or regular), I want to generate API keys from the Web UI, so that I can use them for automated tunnel connections without interactive login.

#### Acceptance Criteria

1. WHEN an authenticated user submits a request to create an API key with a name (1–64 alphanumeric, hyphen, or underscore characters) and an expiration date, THE Token_Generator SHALL create a new API key and return a response containing the plaintext key value, the assigned key ID, and the expiration timestamp exactly once.
2. THE Token_Generator SHALL generate API keys using a cryptographically-secure random generator producing at least 32 bytes of entropy.
3. THE Token_Store SHALL persist only the hashed value (SHA-256) of the API key, never the plaintext.
4. IF the user specifies an expiration date that is in the past or more than 365 days in the future, THEN THE Token_Generator SHALL reject the request with an error message indicating the allowed expiration range.
5. IF the user already has 10 active (non-revoked, non-expired) API keys, THEN THE Token_Generator SHALL reject the creation request with an error message indicating the maximum key limit has been reached.
6. THE Token_Generator SHALL prefix all generated API keys with `gtk_` to distinguish them from JWT tokens.
7. IF the API key name is empty, exceeds 64 characters, or contains characters outside the set [a-zA-Z0-9_-], THEN THE Token_Generator SHALL reject the request with an error message indicating the name validation constraints.
8. IF the API key name is identical to an existing active key name for the same user, THEN THE Token_Generator SHALL reject the request with an error message indicating a duplicate name.

### Requirement 2: API Key Storage

**User Story:** As a system operator, I want API keys stored securely in the database, so that key compromise of the database does not directly expose usable credentials.

#### Acceptance Criteria

1. THE Token_Store SHALL store each API key record with the following fields: id (UUID), user_id (FK to users), name (maximum 100 characters, unique per user), key_hash (SHA-256 hex of the raw key), created_at, expires_at (nullable, where NULL means no expiration), last_used_at (nullable), and status (active/revoked).
2. THE Token_Store SHALL persist only the SHA-256 hash of the raw API key and SHALL NOT store the raw key value at rest in any persistent storage.
3. IF the current time exceeds a key's expires_at value and expires_at is not NULL, THEN THE Token_Store SHALL reject authentication attempts using that key and return an authentication failure indicating the key has expired.
4. IF a key's status is "revoked", THEN THE Token_Store SHALL reject authentication attempts using that key and return an authentication failure indicating the key has been revoked.
5. WHEN the Token_Store returns API key records for a specific user, THE Token_Store SHALL exclude the key_hash field from the response and return only: id, name, created_at, expires_at, last_used_at, and status.
6. THE Token_Store SHALL enforce a maximum of 10 active API keys per user; attempts to create beyond this limit SHALL be rejected with an error indicating the maximum has been reached.

### Requirement 3: API Key Revocation

**User Story:** As a user, I want to revoke API keys that are no longer needed or compromised, so that unauthorized access is prevented.

#### Acceptance Criteria

1. WHEN a user requests revocation of an API key they own, THE Auth_Usecase SHALL delete the key's session entry from the token store within 1 second, causing all subsequent authentication attempts using that key to fail with an unauthorized error.
2. WHEN an admin (role=1) requests revocation of any API key, THE Auth_Usecase SHALL delete the key's session entry from the token store within 1 second, regardless of which user owns the key.
3. IF a non-admin user requests revocation of an API key they do not own, THEN THE Auth_Usecase SHALL reject the request with a forbidden error and leave the target key unchanged.
4. WHEN a user account is deleted, THE Auth_Usecase SHALL revoke all API keys belonging to that user by removing all entries in the user's token set from the token store.
5. WHEN a user account is deactivated (status set to a value other than active), THE Auth_Usecase SHALL revoke all API keys belonging to that user by removing all entries in the user's token set from the token store.
6. WHEN an admin triggers bulk token revocation for a target user, THE Auth_Usecase SHALL revoke all API keys belonging to that target user in addition to any session tokens.
7. IF the token store is unreachable during a revocation request, THEN THE Auth_Usecase SHALL return an error response indicating the revocation could not be completed, and the key SHALL remain in its previous state.

### Requirement 4: Tunnel Authentication with API Key

**User Story:** As a DevOps engineer, I want to use an API key directly in the CLI agent to establish tunnels, so that I can automate tunnel setup without interactive login.

#### Acceptance Criteria

1. WHEN the Tunnel_Server receives a REGISTER message with an auth_token that starts with the prefix `gtk_` followed by at least 1 character, THE Tunnel_Server SHALL route authentication to the API key verification path in Auth_Usecase instead of the JWT verification path.
2. IF the Tunnel_Server receives a REGISTER message with an auth_token equal to `gtk_` with no subsequent characters, THEN THE Tunnel_Server SHALL reject authentication and return an error indicating invalid token format.
3. WHEN an API key is valid (exists in Token_Store, status is active, current time is before expires_at, and the owning user account is active), THE Auth_Usecase SHALL return the owner's User entity populated with id, username, and role fields identical to what JWT-based VerifyToken returns.
4. IF an API key is not found in the Token_Store, or its status is revoked, or current time is at or past expires_at, or the owning user account is inactive, THEN THE Auth_Usecase SHALL reject authentication and return an authorization error without distinguishing which condition failed.
5. WHEN authentication via API key succeeds and the session is established, THE Token_Store SHALL update the last_used_at timestamp for the key asynchronously, such that a failure to update last_used_at does not prevent the tunnel session from being established.
6. WHEN an API key-authenticated session is established, THE Tunnel_Server SHALL enforce domain allowlist checks (IsDomainAllowed with the resolved user's ID and role) and max active tunnels per user limit (GetMaxTunnelsPerUser) identically to JWT-authenticated sessions.

### Requirement 5: CLI Agent API Key Support

**User Story:** As a user, I want to provide an API key to the CLI agent via configuration or environment variable, so that I can run tunnels in headless environments.

#### Acceptance Criteria

1. WHEN the CLI_Agent is invoked with the `--token` flag or `GOTUNNEL_TOKEN` environment variable containing a value prefixed by `gtk_`, THE CLI_Agent SHALL use that value directly as the auth_token in the REGISTER message without performing interactive login, with the `--token` flag taking precedence over the `GOTUNNEL_TOKEN` environment variable when both are present.
2. WHEN both a stored credential (from prior login) and a direct token (via `--token` flag or `GOTUNNEL_TOKEN`) are available, THE CLI_Agent SHALL use the direct token exclusively and ignore the stored credential.
3. IF a direct token authentication fails during tunnel registration, THEN THE CLI_Agent SHALL print the server error message to stderr and exit with status code 1 without retrying the connection.
4. IF the `--token` flag or `GOTUNNEL_TOKEN` environment variable is provided with a value that does NOT start with the `gtk_` prefix, THEN THE CLI_Agent SHALL print an error message indicating the token format is invalid to stderr and exit with status code 1 without attempting a connection.
5. IF no direct token is provided (neither `--token` flag nor `GOTUNNEL_TOKEN` environment variable) and no stored credential exists from a prior login, THEN THE CLI_Agent SHALL print an error message indicating that authentication is required to stderr and exit with status code 1 without prompting for interactive input.

### Requirement 6: Web UI Token Management Page

**User Story:** As a user, I want a dedicated page in the Web UI to manage my API keys, so that I can view active keys, create new ones, and revoke compromised keys.

#### Acceptance Criteria

1. THE Token_Generator SHALL provide a Web UI page accessible to all authenticated users (admin and regular) that lists their API keys sorted by creation date descending, displaying up to 50 keys per page with pagination controls when the total exceeds 50.
2. WHEN the page loads, THE Token_Generator SHALL display for each key: name (1–64 characters), creation date, expiration date, last used date (updated on each authenticated API call using that key), and status (active or revoked).
3. THE Token_Generator SHALL NOT display the key hash or any derivable form of the plaintext key after initial creation.
4. WHEN a new key is created successfully, THE Token_Generator SHALL display the plaintext key exactly once in a modal dialog containing a copy-to-clipboard button and a warning that the key cannot be retrieved again, and SHALL clear the plaintext from the UI upon dialog dismissal.
5. WHEN an admin views the token management page, THE Token_Generator SHALL display API keys from all users with the owner username visible, and SHALL provide a filter input to narrow results by username.
6. IF a user attempts to create an API key that would exceed the maximum of 10 active keys per user, THEN THE Token_Generator SHALL reject the request and display an error message indicating the active key limit has been reached.
7. IF a user requests revocation of an API key, THEN THE Token_Generator SHALL present a confirmation prompt, and upon confirmation SHALL immediately invalidate the key so that subsequent API calls using that key are rejected within 5 seconds.
8. WHEN a user submits the new key creation form, THE Token_Generator SHALL validate that the key name contains only alphanumeric characters, hyphens, and underscores, is between 1 and 64 characters, and is unique among that user's existing keys.

### Requirement 7: API Key Authentication Performance

**User Story:** As a system operator, I want API key authentication to be performant, so that tunnel connections are not delayed by key lookups.

#### Acceptance Criteria

1. WHEN the Tunnel_Server authenticates an API key, THE Auth_Usecase SHALL complete the full lookup and validation (hash computation, database query, status check) in at most 2 database round-trips: one to retrieve the key record by hash, and one to verify the owner user's active status.
2. THE Token_Store SHALL maintain an index on the key_hash column so that a single API key lookup by hash completes in O(log n) time relative to the total number of stored keys.
3. WHEN the Auth_Usecase computes the hash of a presented API key for lookup, THE Auth_Usecase SHALL use SHA-256 (constant-time per input) rather than a computationally-expensive adaptive hash (e.g., bcrypt) to avoid adding latency to every authentication attempt.
4. IF the Token_Store database is unreachable during API key authentication, THEN THE Auth_Usecase SHALL reject the authentication attempt and return an error within 5 seconds (matching the existing connection timeout).
